# sadish 0.9.0 inlines `SdPath`'s points — five rekha programs read the old layout and SIGSEGV

`sd_path_point_x` / `_y` / `sd_path_verb_at`, `[deps.sadish]` moves 0.5.5 → 0.9.0 (commit-pinned

55,320 B of arena against 231,928, and `face_test` asserts capacity == count for all 2,620 glyphs.

## What changed in sadish

`SdPath` stored its points as an array of 8 B POINTERS to separately allocated 16 B `SdPoint` records.
0.9.0 stores the coordinates INLINE — x at +0, y at +8, **16 B a slot**, at the same
`SD_PATH_POINTS_OFFSET` (+16) in the same 48 B record. So `load64(points + i * 8)` now returns half of a
coordinate pair instead of a pointer, and dereferencing it as an `SdPoint` faults.

⭐ **This is the thing rekha asked for.** MEASURED on the proposal's own set — 95 ASCII-shaped paths,
1,768 verbs, 2,498 points, built at exact capacity:

| | bytes | `sd_alloc` calls |
|---|---:|---:|
| sadish 0.8.0 | 78,656 | 2,783 |
| sadish 0.9.0 | **58,672** | **285** |

The proposal's 58,672 B target, to the byte, and a path is now **three allocations** whatever it holds —
the per-point `sd_point_new` that rekha's audit called the dominant remaining emit cost is gone.

## The port

0.9.0 adds the accessors whose absence is why these reads exist. They take an INDEX, so the `* 8`
disappears rather than becoming `* 16`:

```cyr
sd_path_point_x(path, i)    # point i's x, 16.16
sd_path_point_y(path, i)    # point i's y, 16.16
sd_path_verb_at(path, i)    # verb i's tag (the verb stream did NOT change shape)
```

⚠ No bounds check — bound the loop on `sd_path_point_count(path)`, as the old code bounded it.

| suite | site | replacement |
|---|---|---|
| `cff_test` | `:736` `var pts = load64(p + SD_PATH_POINTS_OFFSET);` then `:738-743`, six reads of points 1–3 as `sd_point_x(load64(pts + 8*i))` | drop `pts`; `sd_path_point_x(p, i)` / `sd_path_point_y(p, i)`. Also `:766` `sd_point_x(load64(load64(p + SD_PATH_POINTS_OFFSET) + 24))` → `sd_path_point_x(p, 3)` |
| `glyf_edge_test` | `:632` base + four reads at `:633-636` of `pts + 2 * 8` and `pts + 4 * 8` | `sd_path_point_x(pc, 2)`, `_y(pc, 2)`, `_x(pc, 4)`, `_y(pc, 4)` |
| `hostile_test` | `:311` base + the FNV fold at `:322-329` (`load64(pts + i * 8)`, then `SD_POINT_X_OFFSET` / `_Y_OFFSET`) | `var px = sd_path_point_x(p, i); var py = sd_path_point_y(p, i);` — fold order unchanged, so the stored hashes stand |
| `path_start_test` | the helper `fn ppt(path, i, x, y)` at `:133-137` | the whole helper becomes two accessor checks; every caller unchanged. The cheapest of the five |
| `bench_hotpath` (not a suite) | `:98-103` | `ck = ck * 31 + sd_path_point_x(pth, q) + sd_path_point_y(pth, q) * 7;` |

⚠ `path_test` names `SD_PATH_*` too but is **unaffected** — it reads only `SD_PATH_VERBS_OFFSET`
(`:136`, `:145`), and the verb stream did not change. It is in the 19 that pass.

- ⛔ **How to reproduce, because the mistake is silent:** rekha's manifest is
  `modules = ["dist/sadish.cyr"]`, so it builds against sadish's DIST, not its `src/`. Point

  does not rot is `grep -c '^fn sd_path_point_x' lib/sadish.cyr` — **1** on 0.9.0, **0** on 0.8.0.

## Two figures in rekha's own comments move, in rekha's favour

- `programs/alloc_test.cyr` check #5's comment quotes *"4,192 B of sadish path (sd_path_new 4,144 +
  3 points × 16)"*. It is now **4,144 B in three `sd_alloc` calls**. The assertion is
  `check(glyph_cost > 0, 1)` and still passes — only the comment is stale.
- `proposals/2026-09-15-path-capacity-for-known-size-paths.md` item 3 (rekha adopting
  `sd_path_new_cap`) is still open in sadish and is now worth more: a 26-point glyph at exact capacity
  is **~618 B**.

## Not affected, but worth knowing

sadish's growth ceiling (`sd_grow_limit_set`, `SD_GROW_LIMIT_DEFAULT`) is denominated in BYTES, and a
stroker run point went 8 B → 16 B. sadish **doubled the default to 16 MiB in 0.9.0** so the longest
strokable path is exactly what it was on 0.8.0 — MEASURED, a stroked point costs 40 B of path + run on
both releases, so restoring the length restores the footprint to the byte. rekha does not call
`sd_grow_limit_set` and no glyph outline approaches the ceiling, so nothing here changes. ⚠ A consumer
that tuned its OWN ceiling value should double it.
